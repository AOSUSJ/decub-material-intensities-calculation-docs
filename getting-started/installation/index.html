Instalación y configuración

Requisitos: Git, Python 3.11–3.13 (preferentemente 3.12), y acceso autorizado a PostgreSQL para aplicar migraciones. La documentación y el SQL offline no requieren servidor. Las versiones objetivo de PostgreSQL son 14 y 16, comprobadas mediante una matriz de CI; verificar que ambos trabajos hayan pasado para la revisión que se va a desplegar. Otras versiones requieren validación adicional.

python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev,docs]"

Linux/macOS: source .venv/bin/activate. Ejecutar desde la raíz del repositorio.

Conexión

Copiar .env.example a .env y configurar DECUB_DATABASE_URL con el controlador postgresql+psycopg. Usar las opciones de TLS indicadas por el administrador; codificar caracteres reservados de usuario y contraseña. No incluir secretos en argumentos de terminal, YAML, documentación o commits. El rol de migración necesita permiso de creación de esquemas y tablas en la base autorizada. Usar un rol de acceso limitado para operaciones ordinarias cuando estén disponibles.

Gestión de revisiones

decub db history
decub db migrate --sql
decub db status

--sql genera DDL desde una base vacía, sin conectarse. status consulta la revisión. Antes de aplicar, confirmar base de destino, permisos, ausencia de colisiones de nombres de esquemas y copia de seguridad con el administrador. Alembic utiliza la tabla decub_alembic_version del esquema por defecto; comprobar que no pertenece a otra aplicación.

decub db migrate --apply

Operación administrativa

Este comando modifica PostgreSQL. Solo ejecutarlo en una base autorizada y tras revisar el SQL. No ejecutar migraciones de descenso en producción sin procedimiento de recuperación aprobado.

Documentación y comprobaciones

zensical serve
zensical build --clean --strict
python -m pytest

Zensical genera la web desde Markdown con zensical.toml. El servidor escucha por defecto en http://127.0.0.1:8080/; para usar otro puerto, ejecutar zensical serve -a 127.0.0.1:8081. El servidor local permite consultar la documentación sin publicar información. Las pruebas offline no sustituyen una validación sobre una instancia PostgreSQL aislada.

Comprobar el destino PostgreSQL

Antes de aplicar migraciones, configure la conexión local y ejecute decub db inspect. El comando usa una transacción de solo lectura y devuelve destino, usuario, versión, search_path, privilegios básicos, objetos existentes y tablas de revisión detectadas. No crea esquemas ni modifica datos. Revise autorización y posibles colisiones con otros proyectos; no es una garantía automática de permisos de DDL ni de compatibilidad de la estructura. Su salida contiene información de infraestructura: no publicarla sin revisión.

Importación del inventario HULC

Ejemplo sintético (códigos de identidad definidos por el operador):

 decub import hulc --file "data/hulc/example.xlsm" --study-area area-demo --urban-block block-demo --building building-demo --dry-run

El adaptador espera las hojas Superficies con categorias y Hoja1 con las cabeceras del formato categorizado. Cada archivo representa un único edificio de origen. El código de modelo por defecto es hulc; utilizar --model para otra serie. Mantener los códigos de identidad al actualizar un edificio; no deducir identidades a partir del nombre del fichero. Revisar que el ámbito, manzana y edificio sean los correctos antes de usar --apply. La simulación no escribe datos; la aplicación se ejecuta en una transacción. Los libros y reportes son privados.

Se detectan archivos idénticos por SHA-256 y configuración; una nueva revisión con el mismo contenido físico normalizado conserva el modelo anterior y registra nueva procedencia. Una revisión con cambios genera una instantánea nueva del modelo y de sus composiciones; conserva el historial. No se modifica una versión previa. La comparación ignora orden de elementos y formato, pero conserva orden de partes. No fusiona automáticamente edificios ni composiciones con nombres diferentes. El adaptador presupone que las superficies, espesores y volúmenes de la hoja de composiciones están expresados en m², m y m³; confirmar esta convención en cada fuente. No ejecuta macros ni recalcula fórmulas; conserva expresiones y valores cacheados por separado.

Equivalencias de construcciones

Cuando un nombre de construcción opaca del listado de elementos no coincide con ninguna composición del libro, puede proporcionarse un JSON local mediante --construction-aliases. Cada clave identifica el nombre original sin correspondencia y su valor una composición existente que el operador haya confirmado. Ejemplo sintético (data/hulc/construction_aliases.json):

{
  "Muro de ejemplo": "Composición de ejemplo"
}

 decub import hulc --file "data/hulc/example.xlsm" --study-area area-demo --urban-block block-demo --building building-demo --construction-aliases "data/hulc/construction_aliases.json" --dry-run

Las claves y destinos se normalizan igual que los nombres del libro. Se rechazan claves desconocidas, destinos inexistentes, claves duplicadas tras normalización y sustituciones de coincidencias directas. El informe muestra las equivalencias aplicadas, el número de elementos afectados y las construcciones aún pendientes. Una equivalencia representa una decisión explícita del operador, no una comprobación de equivalencia física realizada por el programa. Revisar las composiciones y sus fuentes antes de confirmar --apply con la misma configuración. Los nombres originales, registros fuente y configuraciones se conservan. Las equivalencias se aplican exclusivamente a cerramientos opacos, no a ventanas. Una configuración distinta de equivalencias efectivas genera una versión de modelo distinta, sin cambiar la identidad del edificio ni de la serie; repetir una configuración ya importada no duplica el modelo. Mantener los JSON reales en el directorio privado data/.

Modos de importación y diagnóstico

Los adaptadores decub import catalog y decub import hulc requieren exactamente uno de estos modos:

Modo Lee y valida el libro Consulta PostgreSQL Persiste cambios
--validate-only Sí No No
--dry-run Sí Sí No
--apply Sí Sí Sí

La validación local revisa el formato admitido, las mediciones, los identificadores y las equivalencias aplicables. Devuelve status: validated, database_checked: false y recuentos del contenido del libro; no son previsiones de inserciones. No puede detectar conflictos con identidades almacenadas, importaciones anteriores, restricciones dependientes de la base ni permisos. En el catálogo, missing_materials y conflicts son null en este modo porque no se han consultado. Las hipótesis constructivas siguen requiriendo confirmación científica.

decub import catalog --file "data/reference/catalog.xlsx" --validate-only
decub import hulc --file "data/hulc/example.xlsm" --study-area area-demo --urban-block block-demo --building building-demo --validate-only

El modo --dry-run requiere conexión y ejecuta una transacción de solo lectura. Si reconoce una configuración ya importada, devuelve already_imported; no valida nuevamente todas las restricciones de una inserción nueva. El modo --apply conserva la atomicidad: todas las escrituras, registros de procedencia y marca de importación completada pertenecen a una única transacción. No hay commits parciales por lote.

flowchart TD
    A[Libro y configuración local] --> B[Lectura y normalización]
    B --> C{Modo}
    C -->|validate-only| D[Informe local]
    C -->|dry-run| E[Consulta de identidades y versiones]
    C -->|apply| F[Bloqueo transaccional y consulta]
    E --> G[Informe de simulación]
    F --> H[Inserciones por lotes ordenados]
    H --> I{Restricciones y commit}
    I -->|Correcto| J[Informe aplicado]
    I -->|Error| K[Rollback]

El diagrama representa dependencias lógicas; los modos con PostgreSQL comprueban la conexión antes de leer el libro. Los mensajes de progreso se envían a stderr y se vacían inmediatamente; los intervalos de filas indican el lote que se está procesando, todavía sin confirmar. Los tiempos son observaciones de la ejecución local, no mediciones científicas. Stdout conserva exclusivamente el informe JSON al finalizar correctamente.

Opción común Valor predeterminado Uso
--batch-size 250 Filas por lote, entre 1 y 1000. No altera la identidad ni el hash del modelo.
--connect-timeout 15 s Límite de conexión libpq por destino, 0 sin límite explícito; sustituye el valor de conexión para esta importación.
--lock-timeout 60 s Límite de espera por cada adquisición de bloqueo, de 0 a 3600 s; 0 lo desactiva. Solo en la transacción de importación.
--quiet No Suprime progreso, no errores ni informe JSON.

Los límites de conexión y bloqueo no son un límite total de ejecución. El tiempo de las consultas puede depender del servidor, los triggers, el volumen y la latencia. Los errores identifican la fase, validaciones controladas o categoría SQLSTATE sin mostrar SQL, parámetros ni excepciones arbitrarias del driver. Ante un error de conexión durante el commit, comprobar el estado de la importación antes de reintentar: no se puede garantizar desde el cliente que el servidor no haya confirmado.

decub import catalog --file "data/reference/catalog.xlsx" --dry-run --connect-timeout 30
decub import hulc --file "data/hulc/example.xlsm" --study-area area-demo --urban-block block-demo --building building-demo --apply --batch-size 250 --lock-timeout 120

No se modifica la base por cambiar el tamaño de lote. No reimportar un modelo ya existente para medir el rendimiento: la ruta idempotente omite las escrituras. Utilizar una base de pruebas aislada con datos sintéticos para medir cargas nuevas.
