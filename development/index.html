Desarrollo y contribución

Usar ramas breves feat/..., fix/..., docs/... y pull requests hacia main. Cada cambio debe incluir las pruebas pertinentes y actualizar la documentación vigente afectada. No crear páginas por cada corrección. Mantener métodos científicos, parámetros, persistencia y visualización separados; evitar valores específicos de materiales incrustados en algoritmos.

python -m pytest
ruff check .
python tools/check_public_tree.py
zensical build --clean --strict

No editar migraciones ya aplicadas; crear una revisión nueva, revisarla y comprobarla contra PostgreSQL aislado. No activar autogeneración sobre esquemas de otras aplicaciones. La publicación de documentación usa únicamente docs/ y recursos públicos.

Publicación web

El repositorio principal puede permanecer privado. El repositorio público hermano decub-material-intensities-calculation-docs (misma organización) contiene exclusivamente la web compilada. No editarlo manualmente: su rama main se reemplaza con los archivos estáticos de cada publicación.

flowchart LR
    A[Markdown en repositorio principal] --> B[Zensical y validaciones]
    B --> C[Repositorio público de documentación]
    C --> D[GitHub Pages]

Configuración inicial por un administrador:

  1. Crear el repositorio hermano público con README y rama main.
  2. En Settings → Pages seleccionar Deploy from a branch, main, / (root).
  3. Crear un token de acceso fine-grained con acceso exclusivo al repositorio público y permiso Contents: Read and write. Guardarlo como secreto de Actions DOCS_PUBLISH_TOKEN en el repositorio principal. No guardarlo en archivos ni compartirlo. La organización puede requerir aprobación.
  4. Revisar los contenidos públicos y ejecutar el workflow Documentation desde main. También se ejecuta al integrar cambios en main.

El workflow compila con la URL pública de la organización, valida tipos de archivo (incluida una excepción de ruta exacta para assets/javascripts/LICENSE de Zensical) y patrones básicos de credenciales, y publica el artefacto estático mediante un trabajo separado. El secreto de publicación solo se usa en ese trabajo. No se copia el historial del repositorio principal. La publicación requiere autorización institucional; los controles automáticos no sustituyen la revisión de contenido. El sitio local conserva su dirección habitual.

Privacidad: no añadir fuentes, datos derivados, geometrías, credenciales o resultados reales al repositorio. .gitignore no elimina archivos ya rastreados; revisar git status y el diff antes de cada commit. Los ejemplos y pruebas deben ser sintéticos. La licencia de distribución requiere confirmación de los responsables.

La comprobación del índice detecta rutas restringidas y algunos patrones de credenciales; no sustituye una revisión de contenidos ni detecta todos los posibles datos sensibles. Ejecutarla después de preparar los cambios para commit.

Integración PostgreSQL

CI ejecuta una matriz de PostgreSQL 14 y 16 con Python 3.12. Cada versión dispone de su propio servicio desechable y ejecuta las mismas comprobaciones, incluidas las migraciones, las pruebas de integración y el ciclo de reversión/reaplicación. Ambos trabajos deben superar las pruebas antes del despliegue. Una versión fallida no cancela la comprobación de la otra. La matriz no utiliza credenciales ni conexiones de producción. Las imágenes oficiales siguen las actualizaciones menores de cada versión mayor.

Las pruebas tests/test_postgres_integrity.py se omiten por defecto. Para ejecutarlas se requiere una instancia aislada con base decub_test, migraciones aplicadas y DECUB_TEST_DATABASE_URL configurada explícitamente. Cada prueba realiza rollback de sus registros sintéticos; las secuencias pueden avanzar. La comprobación CI ejecuta además alembic downgrade base y reaplica las revisiones sobre su servicio desechable. Nunca ejecutar esa reversión contra un servidor de producción. Los triggers se prueban mediante inserciones y actualizaciones, no solo por introspección de metadatos.

Validación del rendimiento de importación

Las pruebas de integración comparan cargas sintéticas equivalentes con tamaños de lote 1 y 10 sobre la misma base aislada, usando un savepoint para deshacer la primera carga. Se cuenta el número de ejecuciones SQL observadas por SQLAlchemy/DBAPI, no se impone un umbral de tiempo dependiente del equipo. También se comprueba la correspondencia entre registros fuente e identificadores, la ausencia de duplicación y el rollback tras una infracción de integridad en un lote posterior. La mejora de tiempo en una conexión remota debe medirse aparte.
