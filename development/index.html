Desarrollo y contribución

Usar ramas breves feat/..., fix/..., docs/... y pull requests hacia main. Cada cambio debe incluir las pruebas pertinentes y actualizar la documentación vigente afectada. No crear páginas por cada corrección. Mantener métodos científicos, parámetros, persistencia y visualización separados; evitar valores específicos de materiales incrustados en algoritmos.

python -m pytest
ruff check .
python tools/check_public_tree.py
python tools/build_docs.py

No editar migraciones ya aplicadas; crear una revisión nueva, revisarla y comprobarla contra PostgreSQL aislado. No activar autogeneración sobre esquemas de otras aplicaciones. La publicación de documentación usa únicamente docs/es/, docs/en/, docs/fr/ y recursos públicos.

Versionado y artefactos generados

La versión del programa sigue MAJOR.MINOR.PATCH (serie 0.x mientras la API y la metodología evolucionan). Incrementar MINOR por hitos funcionales y PATCH por correcciones de una versión publicada; reservar 1.0.0 para una primera versión científica estable y validada. La fuente única es src/decub/__init__.py; setuptools obtiene de ella los metadatos del paquete. Actualizar los README y CHANGELOG en los tres idiomas al cambiar de versión y reinstalar el paquete editable (python -m pip install -e ".[dev,docs,visualization]"). Comprobar decub --version.

Las etiquetas anotadas v0.1.0–v0.7.0 son hitos funcionales retrospectivos establecidos el 26 de noviembre de 2026 sobre commits integrados en main; no representan publicaciones independientes de paquetes ni garantizan que los metadatos históricos coincidan con la etiqueta. No reescribir los commits ni mover las etiquetas existentes. Desde v0.8.0, crear etiquetas anotadas sobre el commit integrado y validado, con versión interna, metadatos y CHANGELOG coherentes. Revisar el commit y publicar la etiqueta explícitamente; una etiqueta no equivale por sí sola a una distribución ni a una GitHub Release. Los cambios exclusivamente documentales posteriores no requieren necesariamente incrementar la versión del programa.

build/ contiene trabajo temporal de Zensical (incluidos los destinos monolingües standalone-es, standalone-en y standalone-fr) y puede contener artefactos de setuptools; dist/ contiene paquetes generados y site/ la web compilada. Los tres directorios se excluyen de Git. Pueden regenerarse; detener antes cualquier compilación o previsualización que los utilice.

Publicación web

El repositorio principal puede permanecer privado. El repositorio público hermano decub-material-intensities-calculation-docs (misma organización) contiene exclusivamente la web compilada. No editarlo manualmente: su rama main se reemplaza con los archivos estáticos de cada publicación.

flowchart LR
    A[Markdown en repositorio principal] --> B[Zensical y validaciones]
    B --> C[Repositorio público de documentación]
    C --> D[GitHub Pages]

Configuración inicial por un administrador:

  1. Crear el repositorio hermano público con README y rama main.
  2. En Settings → Pages seleccionar Deploy from a branch, main, / (root).
  3. Crear un token de acceso fine-grained con acceso exclusivo al repositorio público y permiso Contents: Read and write. Guardarlo como secreto de Actions DOCS_PUBLISH_TOKEN en el repositorio principal. No guardarlo en archivos ni compartirlo. La organización puede requerir aprobación.
  4. Revisar los contenidos públicos y ejecutar el workflow Documentation desde main. También se ejecuta al integrar cambios en main.

El workflow compila con la URL pública de la organización, valida tipos de archivo (incluidas excepciones de ruta exacta para assets/javascripts/LICENSE de Zensical y sus equivalentes en inglés y francés) y patrones básicos de credenciales, y publica el artefacto estático mediante un trabajo separado. El secreto de publicación solo se usa en ese trabajo. No se copia el historial del repositorio principal. La publicación requiere autorización institucional; los controles automáticos no sustituyen la revisión de contenido. El sitio local conserva su dirección habitual.

Privacidad: no añadir fuentes, datos derivados, geometrías, credenciales o resultados reales al repositorio. .gitignore no elimina archivos ya rastreados; revisar git status y el diff antes de cada commit. Los ejemplos y pruebas deben ser sintéticos. La licencia de distribución requiere confirmación de los responsables.

La comprobación del índice detecta rutas restringidas y algunos patrones de credenciales; no sustituye una revisión de contenidos ni detecta todos los posibles datos sensibles. Ejecutarla después de preparar los cambios para commit.

Integración PostgreSQL

CI ejecuta una matriz de PostgreSQL 14 y 16 con Python 3.12. Cada versión dispone de su propio servicio desechable y ejecuta las mismas comprobaciones, incluidas las migraciones, las pruebas de integración y el ciclo de reversión/reaplicación. Ambos trabajos deben superar las pruebas antes del despliegue. Una versión fallida no cancela la comprobación de la otra. La matriz no utiliza credenciales ni conexiones de producción. Las imágenes oficiales siguen las actualizaciones menores de cada versión mayor.

Las pruebas tests/test_postgres_integrity.py se omiten por defecto. Para ejecutarlas se requiere una instancia aislada con base decub_test, migraciones aplicadas y DECUB_TEST_DATABASE_URL configurada explícitamente. Cada prueba realiza rollback de sus registros sintéticos; las secuencias pueden avanzar. La comprobación CI ejecuta además alembic downgrade base y reaplica las revisiones sobre su servicio desechable. Nunca ejecutar esa reversión contra un servidor de producción. Los triggers se prueban mediante inserciones y actualizaciones, no solo por introspección de metadatos.

Validación del rendimiento de importación

Las pruebas de integración comparan cargas sintéticas equivalentes con tamaños de lote 1 y 10 sobre la misma base aislada, usando un savepoint para deshacer la primera carga. Se cuenta el número de ejecuciones SQL observadas por SQLAlchemy/DBAPI, no se impone un umbral de tiempo dependiente del equipo. También se comprueba la correspondencia entre registros fuente e identificadores, la ausencia de duplicación y el rollback tras una infracción de integridad en un lote posterior. La mejora de tiempo en una conexión remota debe medirse aparte.

Pruebas del explorador

CI instala el extra visualization junto con dev y docs. Las pruebas offline comprueban consultas acotadas, parámetros y relaciones, y una prueba de interfaz Streamlit simula configuración ausente. La integración PostgreSQL comprueba consultas reales y el rechazo de escritura en una transacción de solo lectura. La aplicación se ejecuta localmente; no forma parte del artefacto estático de documentación. Las pruebas sintéticas comprueban también el orden y proporción de las franjas, las fracciones de marco, los valores desconocidos y el aislamiento por modelo; la integración prueba que las áreas alternativas no duplican recuentos ni se suman.

Documentación trilingüe

Los README y CHANGELOG del repositorio se mantienen en la raíz en español y en docs/en/ y docs/fr/ para las traducciones. Sus enlaces iniciales permiten cambiar entre las tres versiones. Zensical excluye explícitamente estos documentos de la compilación web; las portadas siguen siendo index.md.

Las fuentes españolas están en docs/es/, las inglesas en docs/en/ y las francesas en docs/fr/, con las mismas rutas relativas. Las configuraciones docs/zensical.es.toml, docs/zensical.en.toml y docs/zensical.fr.toml mantienen navegación equivalente y enlace al repositorio principal. El español es predeterminado; el inglés se publica bajo /en/ y el francés bajo /fr/. En la compilación conjunta, el selector nativo de la cabecera utiliza rutas explícitas desde la raíz de publicación para enlazar con la página equivalente del idioma seleccionado. Un script refuerza el destino del clic y conserva el ancla si su identificador existe en ambas páginas; si no existe, abre la página equivalente sin ancla. El enlace funciona también sin JavaScript. La compilación comprueba cada destino en el HTML final. Para volver a comprobar el sitio existente, ejecutar python tools/build_docs.py --check-links (con el mismo --site-url empleado al compilar, si se especificó). El servidor de edición de un solo idioma no incorpora este procesamiento. El repositorio principal es privado: el enlace no concede permisos de acceso. Las tres configuraciones comparten project.extra.scope (la URL base española, sustituida al compilar para publicación), de modo que la preferencia de tema no depende del idioma. El selector público no modifica el idioma del explorador privado ni el de la CLI.

Actualizar las tres versiones en el mismo cambio, incluidos diccionarios, diagramas, abreviaturas, ejemplos y navegación. Los nombres técnicos, contratos SQL y comandos permanecen iguales. Las comprobaciones de paridad estructural no certifican por sí solas la equivalencia semántica de una traducción; revisar el contenido antes de publicar.

python tools/check_docs_languages.py
python tools/build_docs.py
python -m http.server 8080 --bind 127.0.0.1 --directory site

La compilación estricta de las tres versiones genera site/ solo tras validar los artefactos de cada idioma y combinarlos. Para una URL pública, usar python tools/build_docs.py --site-url https://example.org/docs/ (sustituir por la URL autorizada). La previsualización conjunta permite probar el selector y los enlaces con el servidor local. Las configuraciones permanentes permanecen en docs/; el compilador crea y elimina una configuración temporal en la raíz del repositorio, con rutas relativas de fuentes y salida dentro de esa raíz, como exige Zensical. No ejecutar Zensical directamente con las configuraciones de docs/. Para editar una sola edición, utilizar python tools/build_docs.py --serve-language es (o en o fr); este modo no sirve la compilación conjunta de los tres idiomas. CI y publicación utilizan el mismo compilador; el trabajo de publicación solo recibe el sitio estático validado. Cada configuración declara edit_uri con separadores / y la ruta de su edición en main, para evitar que Zensical derive una URL de edición a partir de una ruta nativa de Windows.

Las pruebas de correspondencias usan datos sintéticos, verifican que las propuestas no asignan materiales, rechazan revisiones obsoletas y decisiones incoherentes, y comprueban el ámbito de partes vinculadas o medidas. La integración PostgreSQL comprueba la simulación, escritura y lectura de una nueva versión y el rechazo de versiones repetidas. Se prueban además nombres multilingües, ambigüedad, etiquetas desactualizadas y persistencia del código resuelto.

Las etiquetas editoriales tienen clave primaria compuesta (entidad e idioma); las pruebas insertan sus registros sintéticos sin exigir un identificador artificial id.

Los recursos de identidad visual se mantienen en src/decub/visualization/assets/. Las tres ediciones documentales incluyen copias idénticas en assets/branding/ para compilarse de forma independiente. Si cambia el logotipo, actualizar todas las copias y el favicon; las pruebas verifican su igualdad. El símbolo ASCII de la CLI es una representación esquemática independiente.
