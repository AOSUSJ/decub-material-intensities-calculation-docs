Catalogue de référence

Le classeur de référence est une source indépendante, non une méthodologie exécutable. L'adaptateur lit les listes de matériaux, codes de composants et grille de typologies dans Hypothèses ; la hiérarchie des déchets et le récapitulatif des masses volumiques dans Code Eural and classification ; les références bibliographiques dans Documentation. Il n'importe ni inventaires de bâtiments, ni tables d'intensités dérivées, ni hypothèses de calcul.

flowchart LR
    A[Classeur] --> B[Normaliser et valider]
    B --> C[Comparer le catalogue existant]
    C --> D[Simulation en lecture seule]
    C --> E[Importation atomique]
    E --> F[Enregistrements sources]
    E --> G[Catalogue versionné]

Exécuter depuis la racine du dépôt :

decub import catalog --file "data/reference/catalog.xlsx" --validate-only
decub import catalog --file "data/reference/catalog.xlsx" --dry-run
decub import catalog --file "data/reference/catalog.xlsx" --apply

Réviser les avertissements, matériaux manquants et conflits avant application. L'application utilise une transaction et un verrou consultatif propre à l'adaptateur. Les autres processus d'écriture ne doivent pas modifier simultanément le même espace de noms importé.

Réimportation et identité

Un fichier binaire identique avec configuration identique et importation terminée ne produit aucune nouvelle écriture. Les identités matérielles sont des empreintes de noms normalisés dans un espace de noms ; le format pris en charge ne dispose pas de codes stables de matériaux. Les codes de déchets ne sont pas des identifiants de matériaux. Renommer un fichier ne change pas son identité. Un fichier modifié peut créer une nouvelle provenance même si les données normalisées correspondent.

Les versions de classification incluent la hiérarchie normalisée et les appartenances ; les modifications créent une nouvelle version en conservant les affectations antérieures. Les changements de masse volumique ou de notes de citation créent des propriétés liées à leur prédécesseur. Les propriétés d'autres sources ne sont pas écrasées. Les noms existants sont conservés et les variantes confirmées stockées comme alias. Les matériaux manquants sont signalés, non supprimés ni retirés. Les ajouts et absences simultanés bloquent l'application sauf résolution explicite ou confirmation de changements indépendants.

Pour un renommage confirmé, utiliser une correspondance JSON locale du nouveau libellé vers le libellé établi :

{"Material sintético renombrado": "Material sintético original"}

Passer --aliases data/reference/aliases.json dans la simulation et l'application et conserver la correspondance pour les futures importations. Utiliser --allow-identity-changes uniquement après révision des ajouts et retraits intentionnels. Aucune correspondance approximative ni inférence des marqueurs de danger manquants. Les entrées bibliographiques et citations de masses volumiques sont des affirmations de la source, non des références vérifiées indépendamment. Les masses volumiques proviennent de cellules numériques mises en cache (kg/m³) ; les valeurs non numériques sont rejetées et les absences ne signifient pas zéro. L'adaptateur prend en charge la disposition fixe observée des feuilles ; les changements de format exigent une révision. La simulation est indicative ; l'application recalcule la comparaison dans sa transaction.

Libellés espagnols, anglais et français

Les noms originaux, codes, alias et propriétés restent intacts. La migration 0009_localization crée des tables de libellés éditoriaux dans les schémas catalog, inventory et sources. Le chargeur explicite utilise un fichier JSON local dans data/, distinct des importations du catalogue. Réviser la provenance et les traductions avant chargement ; ne pas utiliser les libellés comme équivalences scientifiques ou désignations légales vérifiées des déchets.

decub db migrate --apply
decub labels --file data/localization/labels.json --dry-run
decub labels --file data/localization/labels.json --apply

Exemple de format synthétique (le code et l'original doivent exister exactement) :

{
  "format": 1,
  "origin": "Example editorial review",
  "entries": [
    {"entity": "catalog.materials", "code": "synthetic", "source_text": "Synthetic material", "labels": {"es": "Material sintético", "en": "Synthetic material", "fr": "Matériau synthétique"}}
  ]
}

Les nœuds exigent également system_code ; codes et noms originaux doivent correspondre. Les compositions et parties réutilisent les traductions de textes identiques sans inférer une équivalence physique. Les références bibliographiques conservent leurs titres de citation originaux ; les traductions d'affichage ne sont pas de nouveaux titres officiels. Un note facultatif enregistre les incertitudes. Le chargeur valide l'entrée complète avant insertion, réutilise les libellés identiques et rejette les conflits ; l'application est transactionnelle et exige des autorisations d'écriture. La simulation ne modifie pas PostgreSQL. Ne pas exécuter simultanément avec d'autres écrivains. Aucune réimportation de classeur n'est nécessaire pour ajouter des libellés. Les révisions de correspondances conservent leurs empreintes originales ; la recherche scientifique de candidats n'est pas automatiquement élargie. Les textes libres originaux, codes, unités et contenus bruts ne sont ni traduits ni remplacés.

La simulation utilise une transaction PostgreSQL REPEATABLE READ en lecture seule. Si une opération SQL échoue, la commande signale le SQLSTATE lorsqu'il est disponible, sans exposer requêtes ni paramètres privés. Si des tables manquent, vérifier d'abord l'état de la migration 0009_localization.

0011_french_labels étend les sept contraintes de langue. Un fichier contenant uniquement fr est accepté ; les libellés ES/EN existants restent inchangés. La migration ne génère aucune traduction. Le retour à ES/EN échoue si des lignes françaises existent, sans les supprimer.
