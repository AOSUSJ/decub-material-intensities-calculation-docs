Développement et contribution

Utiliser des branches de courte durée feat/..., fix/..., docs/... et des pull requests vers main. Chaque modification doit inclure les tests pertinents et actualiser la documentation courante concernée. Ne pas créer de page pour chaque correction. Séparer méthodes scientifiques, paramètres, persistance et visualisation ; éviter les valeurs propres aux matériaux intégrées dans les algorithmes.

python -m pytest
ruff check .
python tools/check_public_tree.py
python tools/build_docs.py

Ne pas modifier les migrations appliquées ; créer une nouvelle révision, l'examiner et la tester sur PostgreSQL isolé. Ne pas activer l'autogénération pour les schémas d'autres applications. La publication de la documentation utilise uniquement docs/es/, docs/en/, docs/fr/ et les ressources publiques.

Gestion des versions et artefacts générés

Le programme suit MAJOR.MINOR.PATCH (série 0.x pendant l’évolution de l’API et de la méthodologie). Incrémenter MINOR pour les étapes fonctionnelles et PATCH pour les corrections d’une version publiée ; réserver 1.0.0 à une première version stable et scientifiquement validée. La source unique est src/decub/__init__.py ; setuptools en déduit les métadonnées du paquet. Mettre à jour les README et CHANGELOG dans les trois langues lors d’un changement de version et réinstaller le paquet éditable (python -m pip install -e ".[dev,docs,visualization]"). Vérifier decub --version. Ne pas créer de tags rétrospectifs pour des versions non publiées.

build/ contient les fichiers temporaires de Zensical (dont les destinations monolingues standalone-es, standalone-en et standalone-fr) et peut contenir des artefacts de setuptools ; dist/ contient les paquets générés et site/ le site compilé. Ces trois répertoires sont exclus de Git. Ils peuvent être régénérés ; arrêter au préalable toute compilation ou prévisualisation qui les utilise.

Publication web

Le dépôt principal peut rester privé. Le dépôt public frère decub-material-intensities-calculation-docs (même organisation) contient exclusivement le site compilé. Ne pas le modifier manuellement : sa branche main est remplacée par les fichiers statiques à chaque publication.

flowchart LR
    A[Markdown dans le dépôt principal] --> B[Zensical et vérifications]
    B --> C[Dépôt de documentation public]
    C --> D[GitHub Pages]

Configuration initiale par un administrateur :

  1. Créer le dépôt public frère avec README et branche main.
  2. Dans Settings → Pages sélectionner Deploy from a branch, main, / (root).
  3. Créer un jeton d'accès à granularité fine avec accès uniquement au dépôt public et permission Contents: Read and write. Le stocker comme secret Actions DOCS_PUBLISH_TOKEN dans le dépôt principal. Ne pas le stocker dans des fichiers ni le partager. L'organisation peut exiger une approbation.
  4. Réviser le contenu public et exécuter le workflow Documentation depuis main. Il s'exécute également lors de l'intégration des modifications dans main.

Le workflow compile avec l'URL publique de l'organisation, valide les types de fichiers (y compris les exceptions de chemins exacts pour assets/javascripts/LICENSE de Zensical et ses équivalents anglais et français) et les motifs élémentaires de secrets, puis publie l'artefact statique via une tâche distincte. Le secret de publication est utilisé uniquement dans cette tâche. L'historique du dépôt principal n'est pas copié. La publication nécessite une autorisation institutionnelle ; les contrôles automatisés ne remplacent pas l'examen du contenu. Le site local conserve son adresse habituelle.

Confidentialité : ne pas ajouter au dépôt de sources réelles, données dérivées, géométries, identifiants secrets ni résultats. .gitignore ne supprime pas les fichiers déjà suivis ; examiner git status et le diff avant chaque commit. Exemples et tests doivent être synthétiques. La licence de distribution nécessite confirmation des responsables.

Le contrôle de l'index Git détecte des chemins interdits et certains motifs de secrets ; il ne remplace pas l'examen du contenu ni ne détecte toutes les données potentiellement sensibles. L'exécuter après la préparation des modifications pour le commit.

Intégration PostgreSQL

CI exécute une matrice PostgreSQL 14 et 16 avec Python 3.12. Chaque version dispose de son service jetable et exécute les mêmes contrôles, y compris migrations, tests d'intégration et cycle de rétrogradation/réapplication. Les deux tâches doivent réussir avant déploiement. L'échec d'une version n'annule pas l'autre contrôle. La matrice n'utilise ni identifiants ni connexions de production. Les images officielles suivent les mises à jour mineures de chaque version majeure.

Les tests dans tests/test_postgres_integrity.py sont ignorés par défaut. Leur exécution nécessite une instance isolée avec base decub_test, migrations appliquées et configuration explicite DECUB_TEST_DATABASE_URL. Chaque test annule ses enregistrements synthétiques ; les séquences peuvent avancer. CI exécute en outre alembic downgrade base et réapplique les révisions à son service jetable. Ne jamais effectuer cette rétrogradation sur la production. Les déclencheurs sont testés par insertions et mises à jour, et non seulement par introspection des métadonnées.

Validation des performances d'importation

Les tests d'intégration comparent des importations synthétiques équivalentes avec tailles de lot 1 et 10 sur la même base isolée, en utilisant un point de sauvegarde pour annuler la première importation. Ils comptent les exécutions SQL observées par SQLAlchemy/DBAPI ; aucun seuil temporel dépendant de la machine n'est imposé. Ils vérifient également la correspondance entre enregistrements sources et identifiants, l'absence de duplication et l'annulation après violation d'intégrité dans un lot ultérieur. Les gains de temps sur connexion distante doivent être mesurés séparément.

Tests de l'explorateur

CI installe l'extra visualization avec dev et docs. Les tests hors ligne vérifient les requêtes bornées, paramètres et relations, et un test d'interface Streamlit simule une configuration manquante. L'intégration PostgreSQL vérifie les requêtes réelles et le rejet des écritures dans une transaction en lecture seule. L'application s'exécute localement ; elle ne fait pas partie de l'artefact de documentation statique. Les tests synthétiques vérifient aussi l'ordre et les proportions des bandes, les fractions de cadre, les valeurs inconnues et le périmètre du modèle ; les tests d'intégration vérifient que les surfaces alternatives ne dupliquent pas les dénombrements ni ne sont additionnées.

Documentation trilingue

Les fichiers README et CHANGELOG du dépôt restent à la racine en espagnol, avec leurs traductions dans docs/en/ et docs/fr/. Leurs liens initiaux permettent de passer d’une version à l’autre. Zensical exclut explicitement ces documents de la compilation web ; index.md reste la page d’accueil.

Les sources espagnoles se trouvent dans docs/es/, les anglaises dans docs/en/ et les françaises dans docs/fr/, avec les mêmes chemins relatifs. Les configurations docs/zensical.es.toml, docs/zensical.en.toml et docs/zensical.fr.toml maintiennent une navigation équivalente et le lien vers le dépôt principal. L'espagnol est la langue par défaut ; l'anglais est publié sous /en/ et le français sous /fr/. Dans la compilation conjointe, le sélecteur natif de l’en-tête utilise des chemins explicites depuis la racine de publication pour accéder à la page équivalente dans la langue choisie. Un script garantit la destination du clic et conserve l’ancre si son identifiant existe dans les deux pages ; sinon, il ouvre la page équivalente sans ancre. Le lien fonctionne également sans JavaScript. La compilation vérifie chaque destination dans le HTML final. Pour vérifier à nouveau le site existant, exécuter python tools/build_docs.py --check-links (avec le même --site-url que lors de la compilation, si spécifié). Le serveur d’édition monolingue n’intègre pas ce traitement. Le dépôt principal est privé : le lien n'accorde pas d'autorisation. Les trois configurations partagent project.extra.scope (URL de base espagnole, remplacée lors de la compilation pour publication), afin que les préférences du thème soient indépendantes de la langue. Ce sélecteur est propre à la documentation et indépendant de l'explorateur privé.

Actualiser les trois versions dans la même modification, y compris dictionnaires, diagrammes, abréviations, exemples et navigation. Les noms techniques, contrats SQL et commandes restent identiques. Les contrôles de parité structurelle ne certifient pas à eux seuls l'équivalence sémantique des traductions ; examiner le contenu avant publication.

python tools/check_docs_languages.py
python tools/build_docs.py
python -m http.server 8080 --bind 127.0.0.1 --directory site

Les compilations strictes des trois versions génèrent site/ uniquement après validation des artefacts de chaque langue et assemblage. Pour une URL publique, utiliser python tools/build_docs.py --site-url https://example.org/docs/ (remplacer par l'URL autorisée). L'aperçu combiné permet de tester le sélecteur et les liens sur le serveur local. Les configurations permanentes restent dans docs/ ; le générateur crée et supprime une configuration temporaire à la racine du dépôt, avec des chemins relatifs de sources et de sortie à l’intérieur de cette racine, conformément aux exigences de Zensical. Ne pas exécuter Zensical directement avec les configurations de docs/. Pour modifier une seule édition, utiliser python tools/build_docs.py --serve-language es (ou en ou fr) ; ce mode ne sert pas la compilation combinée des trois langues. CI et publication utilisent le même générateur ; la tâche de publication reçoit uniquement le site statique validé. Chaque configuration déclare edit_uri avec des séparateurs / et le chemin de son édition sur main, afin d’éviter que Zensical ne dérive une URL de modification d’un chemin natif Windows.

Les tests de correspondances utilisent des données synthétiques, vérifient que les propositions n'affectent pas de matériaux, rejettent les révisions périmées et décisions incohérentes, et vérifient le périmètre des parties liées ou mesurées. L'intégration PostgreSQL vérifie simulation, écriture et lecture d'une nouvelle version et rejet des versions répétées. Les tests couvrent aussi les noms multilingues, ambiguïtés, libellés périmés et persistance du code résolu.

Les libellés éditoriaux ont une clé primaire composite (entité et langue) ; les tests insèrent des enregistrements synthétiques sans exiger un id de substitution.
