Integrity, conventions and versioning

Internal BIGINT identity identifiers; external TEXT codes independent of IDs; English technical snake_case names; TIMESTAMPTZ dates; initially NUMERIC(24,10) quantities; variable JSONB attributes. Lengths in m, areas in m², volumes in m³, mass in kg, density in kg/m³, fractions between zero and one. Tonnes derived from kg. NULL means unknown, not zero.

Foundation migrations implement keys, uniqueness, restricted-delete references, FK indexes and range consistency checks. Revision 0006_integrity strengthens declarative constraints with PostgreSQL functions and triggers for hierarchies, densities, classification domains and mapping selection. Scientific compatibility of methods and profiles still requires application validation. Do not assume a future constraint already exists.

A fingerprint does not replace retaining inputs. Reproducible results require references to exact versions and properties. Do not silently modify used versions. Inventory uses composite FKs to protect consistency of level, identifier and element type, successor model series and nested part version. Partial unique indexes protect order among sibling parts. Complete version immutability, element relationship semantics, units and double counting require later validation. Do not enable partitioning or indiscriminate indexes without measurements.

Methodology enforces uniqueness of versions, roles, assumptions and interpretations within their scopes, fractions between zero and one, explicit basis and JSONB objects. Validation of sums, method compatibility, sufficient assignments and immutability remains pending in Python services.

Results adds composite FKs between run, model, element, assembly, part, mapping set and material assignment; it checks that the referenced property corresponds to the material. Model aggregates have unique grain even with NULL dimensions. Unknown quantities remain NULL; coverage, classification and method version selection and calculation consistency require application validation. See results.

Systems can retain other nonempty domains, but cannot be used in these associations without explicitly extending the contract. System domain, version system, node version, property type code/canonical unit and property type are not editable after creation. New identities or versions will be created when necessary. Descriptive names remain editable; this is not equivalent to freezing a scientific dataset.

Execution and concurrency

Triggers are installed via Alembic, not metadata.create_all(); alembic check does not itself verify functions or triggers. CI runs insertion and rejection tests against isolated PostgreSQL and a downgrade/reapply cycle. Hierarchy checks traverse the entire graph after each relevant statement and serialize writes with SHARE ROW EXCLUSIVE. Import in batches and use READ COMMITTED (default); conflicts/deadlocks may require retrying the entire transaction. REPEATABLE READ is rejected for hierarchy writes and mapping selection; SERIALIZABLE requires retry handling. Performance and concurrency have not yet been measured. Hierarchy-writing roles need permission to acquire that lock.

The migration also checks existing rows through logically unchanged updates; an incompatible record aborts migration rather than being corrected or deleted automatically. Downgrade removes only the added constraints and triggers.

Limits

Complete version and dependency closure, scientific selection of methods and measurements, dimensional and bulk/intrinsic density compatibility and double-count prevention are still missing. Later revisions incorporate aggregate contributions and selected-input sealing. A FK or trigger alone does not ensure scientific validity.

Result resolution (0007_resolution)

The scope constraint distinguishes element, part measurement and component contributions; it retains existing FKs and requires a complete chain where applicable. Partial indexes limit scope duplicates; the trigger checks the component domain. Selection of nonoverlapping scopes and input sufficiency remain pending in the Python engine. Downgrade rejects existing aggregate data. See results.

Reproducibility (0008_reproducibility)

  • The manifest is generated in PostgreSQL from an explicit selection; the snapshot is retained and fingerprint computed without converting numeric values to float in Python.
  • Triggers prevent updating or deleting sealed inputs, altering sealed configuration and models or modifying results of finalized runs. They do not prevent new rows in logical sets; complete selection remains the scientific service’s responsibility.
  • Sealing takes SHARE locks on selected tables in stable order and requires READ COMMITTED isolation; input updates and deletions also require that isolation. Result writes lock their run to serialize with sealing/finalization. Keep transactions short and retry transactions aborted by deadlock. Concurrency and performance require representative tests.
  • Downgrade is blocked if manifests, finalized runs or explicit measurements in quantities exist, preventing loss of historical protection.
  • Triggers protect ordinary DML operations, not administrative operations such as disabling triggers or truncating tables. Separate migration/administration role from application role and do not grant TRUNCATE or DDL to the latter.
  • Do not duplicate the entire database: select only relevant inputs. The manifest may contain private source records and remains in the database; never publish it in documentation or repositories.
