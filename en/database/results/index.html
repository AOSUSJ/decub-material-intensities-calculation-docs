Results — relational model

Revision 0005_results implements seven tables for optional result persistence. The Python calculation engine and writing services are not yet implemented. PostgreSQL stores provenance and quantities; it does not execute scientific formulas.

    CALCULATION_RUNS ||--o{ RUN_MODELS : scope
    BUILDING_MODELS ||--o{ RUN_MODELS : included
    RUN_MODELS ||--o{ MATERIAL_QUANTITIES : produces

Grain and scope

Table Grain
calculation_runs One scientific run
run_models One included model per run
material_quantities One material contribution per run, according to its resolution
material_totals One model and dimension combination per run
indicator_definitions One versioned ratio indicator definition
indicator_values One model, versioned indicator and dimension combination per run
calculation_issues One run issue, with optional context

Persisted totals and indicators are initially limited to a model. Aggregates for buildings with several models, blocks and areas will be calculated in Python, selecting nonoverlapping representations. Different versions of a building will not be added as if they were different buildings. Each total may refer to a material, a material category or all materials; optionally it is disaggregated by component. Classification nodes already identify a version. Groups at different levels are not additive: do not mix overall totals with breakdowns. Domains are validated in PostgreSQL since 0006_integrity; consistent version selection belongs to the service.

Data dictionary

IDs are BIGINT identity and PK. FKs use restricted deletion. Physical values use NUMERIC(24,10); NULL means unknown. JSONB objects do not contain executable code. Composite keys are listed explicitly below each table.

Cross-schema consistency

The revision adds five UNIQUE constraints to existing tables so that composite result FKs can check identifiers and their scopes together. It does not change earlier revisions.

Table Supporting unique key
inventory.element_constructions uq_ec_result_scope: id, element_id, construction_version_id
inventory.building_measurements uq_bm_result_scope: id, building_model_id
methodology.part_mappings uq_pm_result_scope: id, mapping_version_id, construction_part_id
methodology.material_assignments uq_ma_result_scope: id, part_mapping_id, material_id
catalog.material_properties uq_mp_result_material: id, material_id

The material quantity must belong to the model included in the run. At element resolution, it must belong to the element assembly; the part must belong to the correct assembly version, and the assignment must belong to the mapping of that part and the set selected by the run. The density property, if referenced, must correspond to the same material. Effective density is retained numerically; revision 0006_integrity requires the referenced property to be of type density in kg/m3, with positive finite values. Selection of the effective value and its physical basis belongs to the engine. PostgreSQL requires a fixed profile mapping to match the run mapping; review statuses and scientific method selection will be validated in Python. A valid reference is not assumed to be scientifically appropriate.

Statuses and unknown quantities

Status Volume and mass
calculated Both reported
estimated Both reported, traceable assumption
partial At least one quantity reported; may be known subtotals
pending Both NULL
excluded Both NULL
confirmed_absent Both zero, justified absence

Parts not yet associated with a material will be recorded as issues, not artificial materials. A completed run status indicates that it has finished, not that its inventory is complete. Services must validate justifications, mapping statuses and completeness. Partial quantities must not be confused with complete totals. Aggregate unique indexes treat NULL dimensions as the same absence (using coalesce to 0); generated identifiers are positive.

Indicators and coverage

Initial indicators are nonnegative ratios with a positive denominator from a measurement of the same model. An absent measurement may leave the denominator and indicator NULL. The engine must validate units, measurement type, ratio calculation and denominators; the database does not recalculate formulas. Indicator definitions are versioned so that changes in units or meaning do not replace historical values.

Mass and volume coverage are independent, optional and between zero and one. If coverage is known, its basis is recorded; details can retain numerator, denominator and coverage scope. A universal coverage formula is not yet defined. The engine must check that coverage is interpretable, not estimate it merely from row count. Actual results remain in authorized private storage.

Synthetic example

A contribution with known volume and unknown density has NULL mass and partial status. Another contribution with known mass can be aggregated, but the total must declare that it is partial. Unknown mass is not converted to zero, nor is the percentage of complete contributions interpreted as the percentage of known mass.

Reproducibility and persistence

Each run retains profile, mappings, code version, configuration and SHA-256 fingerprint. Revision 0008_reproducibility adds a selected-input manifest and protects finalized results. The engine must identify all effective dependencies and consume sealed inputs; fingerprint format alone does not guarantee scientific reproducibility. The commit is optional. Writer, aggregator, indicator calculation and automatic retention policy do not yet exist. Detailed persistence is optional.

0006_integrity adds unique keys (id, building_model_id), (id, element_id) and (id, construction_part_id) in material_quantities, and corresponding composite FKs in calculation_issues. If a quantity is reported, every non-null dimension of the issue must match it; an omitted dimension can be derived from the quantity. See integrity.

Contribution resolution

Revision 0007_resolution retains the seven schema tables. No fictitious elements are created to store estimates or aggregate measurements.

flowchart TD
    E[Element and assembly] --> Q[Material contribution]
    P[Part measurement and model] --> Q
    B[Building measurement or source record] --> Q
    Q --> V[Selection of nonoverlapping scopes in Python]
    V --> T[Totals and indicators]
Resolution Additional mandatory references Prohibited references
element Element, element-assembly association, version, part and mapping chain Aggregate fields
part_measurement Version, part, mapping chain, part measurement, component, coverage key Element, element-assembly association, building measurement
component Component, coverage key and at least one building measurement or original record Element, assembly, part, part measurement and mapping chain

Run, model, material and method are mandatory in every case. A component result may come from an external measurement or direct estimate without layer-level mapping; the method and calculation details must explain its interpretation. A reference to an original record alone does not establish that it belongs to the model: the importer or service must check this. Partial quantities can be retained, e.g. mass without volume. Measurements may be pending; sufficiency and units will be validated in Python.

coverage_key identifies a stable physical scope within the model. It must be reused for alternative measurements of the same scope; it is not a file fingerprint or geometry identity. Partial indexes prevent exact duplicates by scope and contribution but do not establish that two different scopes do not overlap. Do not automatically add rows of different resolution: first select a nonoverlapping representation for each physical component. A part result and a component result may be alternatives, not additive quantities. This policy and its manifest still require Python implementation.

Downgrade to 0006_integrity is rejected if aggregated contributions exist, to avoid data loss. Previous rows retain their element resolution.

Input and result sealing (0008_reproducibility)

calculation_runs.input_manifest is a nullable JSONB object until sealing. material_quantities.element_measurement_id (nullable BIGINT) references (id, element_id) in inventory.element_measurements, with FK fk_mq_element_measurement_scope, an index and CHECK requiring element resolution when supplied. An area is not required when the method does not use it.

flowchart LR
    A[Create running run] --> B[Register models]
    B --> C[Select inputs and parameters]
    C --> D[Seal manifest and SHA-256]
    D --> E[Calculate from sealed inputs]
    E --> F[Persist contributions and indicators]
    F --> G[Finalize and freeze results]

The decub.pg-jsonb.v1 manifest contains rows (table, identifier, complete record), parameters, models, profile, mappings, configuration, code version, commit and run type. SHA-256 is calculated over the PostgreSQL JSONB textual representation in UTF-8; interoperable canonical serialization across engines or PostgreSQL versions is not promised. The exact document is retained, not just its fingerprint.

The decub.results.reproducibility.seal_run(connection, run_id, selection, parameters) service requires a caller-controlled transaction and returns the fingerprint. Selection is a map of qualified table names to positive identifiers. The profile, mappings if present and all registered models are required. Synthetic example:

from decub.results.reproducibility import seal_run

# Inside a transaction, after registering the run and its models.
fingerprint = seal_run(connection, run_id, {
    "methodology.profile_versions": [profile_id],
    "methodology.mapping_versions": [mapping_id],
    "inventory.building_models": [model_id],
    # Add all other effective inputs of the method.
}, parameters={})

The example is not a sufficient selection to calculate a real building. PostgreSQL captures records and rejects completion if direct references of quantities, aggregates and indicators are not selected. Transitive dependency closure is not discovered automatically and scientific validity of parameters is not verified. Calculation details must record additional inputs per contribution where appropriate.

A sealed run retains its configuration and models; while running it accepts result writes. Upon finalization (completed, failed, cancelled), run rows and results are protected against ordinary changes. Earlier historical runs without a manifest do not become reproducible retroactively. New runs are created running without a manifest; a provisional 64-character hexadecimal fingerprint is replaced when sealed and is not a scientific fingerprint. Only completed requires a manifest; failures and cancellations before sealing are possible.

Sealing retains and protects selected records, not every row in a logical version. New observations or versions may be added without changing sealed records. The engine must use only the fixed selection, not indiscriminately query new rows of a version. Complete version and dependency closure policy remains pending.
