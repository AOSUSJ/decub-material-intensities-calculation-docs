Development and contribution

Use short-lived feat/..., fix/..., docs/... branches and pull requests to main. Each change must include relevant tests and update affected current documentation. Do not create pages for every correction. Keep scientific methods, parameters, persistence and visualization separate; avoid material-specific values embedded in algorithms.

python -m pytest
ruff check .
python tools/check_public_tree.py
python tools/build_docs.py

Do not edit applied migrations; create a new revision, review it and test it against isolated PostgreSQL. Do not enable autogeneration for schemas of other applications. Documentation publication uses only docs/, docs-en/ and public resources.

Web publication

The main repository may remain private. The sibling public repository decub-material-intensities-calculation-docs (same organization) contains exclusively the compiled website. Do not edit it manually: its main branch is replaced by static files on each publication.

flowchart LR
    A[Markdown in main repository] --> B[Zensical and checks]
    B --> C[Public documentation repository]
    C --> D[GitHub Pages]

Initial configuration by an administrator:

  1. Create the sibling public repository with README and main branch.
  2. In Settings → Pages select Deploy from a branch, main, / (root).
  3. Create a fine-grained access token with access only to the public repository and Contents: Read and write permission. Store it as Actions secret DOCS_PUBLISH_TOKEN in the main repository. Do not store it in files or share it. The organization may require approval.
  4. Review public content and run the Documentation workflow from main. It also runs when changes are integrated into main.

The workflow builds with the organization's public URL, validates file types (including exact path exceptions for Zensical's assets/javascripts/LICENSE and its English counterpart) and basic credential patterns, and publishes the static artifact through a separate job. The publishing secret is used only in that job. The main repository history is not copied. Publication requires institutional authorization; automated checks do not replace content review. The local site retains its usual address.

Privacy: do not add actual sources, derived data, geometries, credentials or results to the repository. .gitignore does not remove already tracked files; review git status and the diff before each commit. Examples and tests must be synthetic. The distribution license requires confirmation from the responsible parties.

The Git index check detects restricted paths and some credential patterns; it does not replace content review or detect all potentially sensitive data. Run it after staging changes for commit.

PostgreSQL integration

CI runs a PostgreSQL 14 and 16 matrix with Python 3.12. Each version has its own disposable service and executes the same checks, including migrations, integration tests and the downgrade/reapply cycle. Both jobs must pass before deployment. A failed version does not cancel the other check. The matrix does not use production credentials or connections. Official images follow minor updates for each major version.

Tests in tests/test_postgres_integrity.py are skipped by default. Running them requires an isolated instance with database decub_test, applied migrations and explicit DECUB_TEST_DATABASE_URL configuration. Each test rolls back synthetic records; sequences may advance. CI additionally runs alembic downgrade base and reapplies revisions to its disposable service. Never perform that downgrade against production. Triggers are tested by inserts and updates, not merely by metadata introspection.

Import performance validation

Integration tests compare equivalent synthetic imports with batch sizes 1 and 10 on the same isolated database, using a savepoint to undo the first import. They count SQL executions observed by SQLAlchemy/DBAPI; no machine-dependent time threshold is imposed. They also check correspondence between source records and IDs, absence of duplication and rollback following an integrity violation in a later batch. Time improvements over a remote connection must be measured separately.

Explorer tests

CI installs the visualization extra together with dev and docs. Offline tests check bounded queries, parameters and relationships, and a Streamlit interface test simulates missing configuration. PostgreSQL integration checks actual queries and rejection of writes in a read-only transaction. The application runs locally; it is not part of the static documentation artifact. Synthetic tests also check strip order and proportions, frame fractions, unknown values and model scoping; integration tests check that alternative areas do not duplicate counts or get summed.

Bilingual documentation

Spanish sources are in docs/, English sources in docs-en/, with matching relative paths. The zensical.toml and zensical.en.toml configurations maintain equivalent navigation and the main repository link. Spanish is the default; English is published under /en/. The native header selector links to the selected language's home page. The main repository is private: the link does not grant access permissions. Both configurations share project.extra.scope (the Spanish base URL, replaced when building for publication), so theme preferences are independent of language.

Update both versions in the same change, including dictionaries, diagrams, abbreviations, examples and navigation. Technical names, SQL contracts and commands remain identical. Structural parity checks do not certify translation semantic equivalence on their own; review content before publication.

python tools/check_docs_languages.py
python tools/build_docs.py
python -m http.server 8080 --bind 127.0.0.1 --directory site

Strict builds of both versions generate site/ only after validating each language's artifacts and combining them. For a public URL, use python tools/build_docs.py --site-url https://example.org/docs/ (replace with the authorized URL). The combined preview allows testing the selector and links with the local server. zensical serve remains useful for editing the Spanish version but does not serve the combined build of both languages. CI and publication use the same builder; the publishing job receives only the validated static site.

Mapping tests use synthetic data, verify that proposals do not assign materials, reject stale reviews and inconsistent decisions, and check the scope of linked or measured parts. PostgreSQL integration checks simulation, writing and reading a new version and rejection of repeated versions. Tests also cover multilingual names, ambiguity, stale labels and persistence of the resolved code.

Editorial labels have a composite primary key (entity and language); tests insert synthetic records without requiring a surrogate id.
