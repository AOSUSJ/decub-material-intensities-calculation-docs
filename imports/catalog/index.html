Catálogo de referencia

El libro de referencia es una fuente independiente, no una metodología ejecutable. El adaptador lee las listas de materiales, códigos de componentes y cuadrícula de tipologías de Hypothèses; la jerarquía de residuos y el resumen de densidades de Code Eural and classification; y las referencias bibliográficas de Documentation. No importa inventarios de edificios, tablas derivadas de intensidades ni hipótesis de cálculo.

flowchart LR
    A[Libro] --> B[Normalizar y validar]
    B --> C[Comparar catálogo existente]
    C --> D[Simulación de solo lectura]
    C --> E[Importación atómica]
    E --> F[Registros fuente]
    E --> G[Catálogo versionado]

Ejecutar desde la raíz del repositorio:

decub import catalog --file "data/reference/catalog.xlsx" --validate-only
decub import catalog --file "data/reference/catalog.xlsx" --dry-run
decub import catalog --file "data/reference/catalog.xlsx" --apply

Revisar advertencias, materiales ausentes y conflictos antes de aplicar. La aplicación usa una transacción y un bloqueo asesor específico del adaptador. Otros escritores no deben modificar simultáneamente el mismo espacio de nombres importado.

Reimportación e identidad

Un archivo binario idéntico con configuración idéntica e importación completada no produce nuevas escrituras. Las identidades de materiales son hashes de nombres normalizados dentro de un espacio de nombres; el formato admitido no tiene códigos de material estables. Los códigos de residuos no son identificadores de material. Cambiar el nombre del archivo no cambia su identidad. Un archivo modificado puede generar nueva procedencia aunque los datos normalizados coincidan.

Las versiones de clasificación incluyen jerarquía y pertenencias normalizadas; los cambios generan una nueva versión conservando asignaciones anteriores. Cambios de densidad o notas de cita generan propiedades enlazadas a su predecesora. No se sobrescriben propiedades de otras fuentes. Se conservan nombres existentes y las variantes confirmadas se guardan como alias. Los materiales ausentes se notifican, no se eliminan ni retiran. Altas y ausencias simultáneas bloquean la aplicación salvo resolución explícita o confirmación de que son cambios independientes.

Para un cambio de nombre confirmado, utilizar un JSON local de etiqueta nueva a etiqueta establecida:

{"Material sintético renombrado": "Material sintético original"}

Pasar --aliases data/reference/aliases.json tanto en simulación como en aplicación y conservar el mapa para futuras importaciones. Usar --allow-identity-changes solo tras revisar altas y bajas intencionadas. No hay coincidencia difusa ni inferencia de marcadores de peligrosidad ausentes. Las entradas bibliográficas y citas de densidad son afirmaciones de la fuente, no referencias verificadas independientemente. Las densidades proceden de celdas numéricas cacheadas (kg/m³); se rechazan densidades no numéricas y las ausentes no equivalen a cero. El adaptador admite el diseño fijo observado de las hojas; cambios de formato requieren revisión. La simulación es orientativa; la aplicación recalcula la comparación en su transacción.

Véase modos y diagnóstico, persistencia del catálogo y procedencia.

Etiquetas en español, inglés y francés

Las denominaciones originales, códigos, alias y propiedades permanecen intactos. La migración 0009_localization crea tablas de etiquetas editoriales en los esquemas de catálogo, inventario y fuentes. El cargador explícito trabaja con un JSON local en data/, separado de la importación del catálogo. Revisar la procedencia y la traducción antes de cargar; no usar etiquetas como equivalencias científicas o como denominaciones legales verificadas de residuos.

decub db migrate --apply
decub labels --file data/localization/labels.json --dry-run
decub labels --file data/localization/labels.json --apply

Ejemplo sintético del formato (el código y el original deben existir exactamente):

{
  "format": 1,
  "origin": "Revisión editorial de ejemplo",
  "entries": [
    {"entity": "catalog.materials", "code": "synthetic", "source_text": "Synthetic material", "labels": {"es": "Material sintético", "en": "Synthetic material", "fr": "Matériau synthétique"}}
  ]
}

Para nodos se exige también system_code; los códigos y el nombre original deben coincidir. En composiciones y partes se reutilizan traducciones de texto idéntico, sin inferir equivalencia física. Las referencias bibliográficas conservan su título de cita original; la traducción de presentación no es un nuevo título oficial. Un note opcional documenta dudas. El cargador valida toda la entrada antes de insertar, reutiliza etiquetas idénticas y rechaza conflictos; la aplicación es transaccional y requiere permisos de escritura. La simulación no modifica PostgreSQL. No ejecutar simultáneamente con otros escritores. No reimportar los Excel para añadir etiquetas. Las revisiones de correspondencias conservan su huella original; no se amplía automáticamente la búsqueda científica de candidatos. Los valores originales de campos libres, códigos, unidades y payloads no se traducen ni se sustituyen.

La simulación utiliza una transacción PostgreSQL REPEATABLE READ de solo lectura. Si falla una operación SQL, el comando indica el SQLSTATE cuando está disponible, sin mostrar consultas ni parámetros privados. Si faltan tablas, comprueba primero el estado de la migración 0009_localization.

0011_french_labels amplía las siete restricciones de idioma. Se admite un archivo con solo fr; las etiquetas ES/EN existentes no se modifican. La migración no genera traducciones. Una reversión a ES/EN falla si existen filas francesas, sin borrarlas.
